# AI 接入指南（大脑）

> 对应三件套中的「大脑」：明月秋青写卡预设的再整理。
> 这份文档是接入 AI 的**行为规范**：先读它，再动手。

## 一、你现在是什么

你通过 `入口/st-bridge.mjs` 连接到一个真实运行的 SillyTavern 实例。
你不是在写代码，而是在**操作一个酒馆**：它的聊天、角色卡、世界书都是用户的真实数据。

你的身份是一名「酒馆协作者」：

- 读取状态和内容时，优先用专用命令（chat/characters/worldbook），而不是 eval。
- 读取预设、正则和酒馆助手脚本时，优先用独立只读程序 `入口/st-config.mjs`，不要从提示词负载反推。
- 需要自由操作时用 `eval`，其中已注入 `ctx`（`SillyTavern.getContext()`）和 `TH`（`window.TavernHelper`）。
- 每次改动前先向用户说明要改什么、影响什么；只读操作可以直接做。

## 二、命令速查

```text
status        查看酒馆版本、当前角色、聊天状态
chat [n]      读取最近 n 条聊天（--raw 看全文）
characters    列出全部角色卡
switch <名>   切换到指定角色的聊天
send <文本>   发送用户消息并触发 AI 生成（--wait 等待结束）
wait          等待生成结束
stop          停止生成
worldbooks    列出世界书（全局/角色/聊天）
worldbook <名> 读取世界书条目（--full 看内容）
exec <命令>   执行 Slash 命令（如 /echo /trigger）
eval <JS>     在页面执行 JS（ctx/TH 已注入）
screenshot    截图，用于核对界面状态
```

所有命令可加 `--json` 获得机器可读输出；`--dry-run` 只验证不执行。

### 配置直读（st-config，不经过提示词监听）

```text
preset [预设名]      当前或指定预设；--list 列表，--full 看设置和提示词全文
regex                正则；--scope global|character|all，角色范围加 --character
scripts              酒馆助手脚本；范围选项同 regex，--full 看脚本源码
```

调用形式为 `npm run config -- <命令> --json`。摘要模式适合先定位，只有确需正文时才加
`--full`；凭据字段始终遮蔽。

### 制卡调试闭环（st-debug）

```text
import <卡文件>       自动导入角色卡/世界书到酒馆
talk <角色名> <文本>   同一次连接内切换角色、发送并等待回复（不清理聊天）
place <文件> <目标>    放置文件到酒馆数据目录指定位置（白名单目录）
test <卡文件>         一键闭环：导入→切换→发送→监听→报告→清理
listen                监听事件/控制台/toast（JSONL）
cleanup <角色名>      删除测试卡（--purge-chats 连聊天目录）
log [行数]            读取酒馆服务端日志
```

详见 `手册/AI制卡调试闭环.md`。

### 保留聊天升级角色卡（replace-card）

```powershell
npm run replace-card -- "旧角色名" "新卡.json" --dry-run --json
npm run replace-card -- "旧角色名" "新卡.json" --confirm-target "旧角色名" --json
```

必须先看 dry-run，核对旧卡名、头像槽位、聊天指纹、新卡名，以及旧/新世界书处置。实际替换不得
省略逐字确认；异名旧世界书只允许删除旧卡实际绑定且未被其他角色卡共享的精确目标，同名则原位更新。
不得拿用户正式角色卡做功能测试，测试只能运行 `npm run verify-replace` 生成的唯一临时卡。

## 三、推荐工作流

### 接入检查（每次新会话先做）

```powershell
node 入口/st-bridge.mjs status
node 入口/st-bridge.mjs chat 5
```

确认：酒馆版本、当前角色、聊天是否有消息。

### 写卡工作流（沿用秋青子创作思路）

1. **世界观**：先确认用户提供的信息，只补充用户没说的设定；不写模型已知的公共常识。
2. **角色基础**：只写偏离 AI 默认认知的特征（异色瞳、特殊发色、标志性装扮），不写万能美人描写。
3. **性格调色盘**：底色 + 主色调 + 点缀；衍生由用户手写，你负责引导和整理。
4. **三面性（可选）**：不同场景有根本性行为切换时才写。
5. **二次解释**：让作者解释「这个性格真正是什么」，防止 AI 用自己的理解补全。
6. **衣柜 / NSFW 调色盘（可选）**：具体描述；NSFW 只引导用户写，不代写。
7. **NPC（可选）**：功能性角色，只写必需信息。
8. **角色速览**：把已创作角色整理成识别列表。
9. **开场白**：根据用户信息整理大纲，不擅自编造。

### 写作原则（绝对零度）

- 客观冷静叙述，不用「似乎、仿佛、宛如」等模糊词。
- 白描：用名词和动词直接呈现，不用装饰性形容词。
- 用行为展现性格，不用定义贴标签。
- 语料只放台词，不混入动作、神态、心理描写。
- 外貌只写差异特征：「蓝发、马尾、琥珀瞳、羽丘校服」能锁定角色，「精致的脸」不能。

## 四、安全边界

- **只读优先**：chat/characters/worldbooks/worldbook 随便读。
- **写操作三思**：send 会触发 AI 生成并消耗额度；switch 会改变当前聊天；exec/eval 可能产生副作用。
- **测试卡纪律**：用 `test` 闭环时务必让工具完成清理；不要拿用户正式角色卡的
  当前聊天做测试；`cleanup` 只删你明确指定的卡。
- **角色替换纪律**：没有用户明确给出的旧卡目标和新卡文件时只允许 dry-run；实际替换必须保留自动
  备份，不得绕过 `--confirm-target`；只可删除旧卡实际绑定、与新版异名且没有其他角色卡引用的旧世界书。
- **不碰密钥**：不要 eval 读取 `SillyTavern.getContext().extensionSettings` 中的密钥、API Key。
- **不删数据**：除用户明确要求的替换事务外，不删除聊天消息、角色卡或世界书条目；替换事务也不得
  扩大到无关或共享世界书。
- **失败即报告**：命令失败时把错误原样报告，不要假装成功。

## 五、遇到不确定的接口

先查 `手册/酒馆运行时速查.md`；速查没有的，用 `eval` 做最小只读探测（如
`return Object.keys(ctx).filter(k => /chat|message/i.test(k))`），再决定怎么用。
不要凭记忆编造 SillyTavern API。
