# 《道渊》v5.3 超级大卡完整逆向报告

分析日期：2026-08-09（Asia/Shanghai）

分析对象：用户提供的角色卡 PNG

本报告的目标不是评价其美术或状态栏外观，而是回答四个问题：

1. PNG 中究竟装了什么，319 条世界书怎样被保存和导入。
2. 319 条世界书在运行时怎样分层、激活和控制上下文。
3. MVU、Zod、EJS、助手脚本、正则和开局创建器怎样共同工作。
4. 哪些设计值得本项目复用，哪些缺陷不能照搬。

## 0. 结论先行

这张卡的核心不是“每轮把 319 条世界书全部喂给模型”，而是一个四层系统：

    公共常驻规则
      + 当前界域的 EJS 聚合包
      + 本轮关键词命中的叶子知识
      + 贴在 D0 附近的 MVU 状态与更新协议

319 条世界书中：

| 层级 | 条目数 | 字符 | cl100k_base 近似 token | 运行方式 |
|---|---:|---:|---:|---|
| 已启用常驻 | 30 | 31,272 | 30,554 | 原生激活阶段常驻；后续可能被 MVU 模型路由过滤 |
| 已启用关键词叶子 | 265 | 150,623 | 197,244 | 人物、地点、势力、器物等按聊天关键词命中 |
| 禁用聚合包与备用协议 | 24 | 28,249 | 30,530 | 由 EJS 直接读取，或留作模式切换 |
| 合计 | 319 | 210,144 | 258,328 | 完整知识资产 |

默认玄天界的**预路由静态源文本等价估算**并不轻：排除路由器自身源码后，29 条公共常驻源码加 10 条由 EJS 展开的玄天界模块，共 46,336 字符，cl100k_base 约 48,830 token。仙界对应静态估算为 36,180 字符、36,891 token。它不是任一模型的真实固定请求：UID 227/229 会被 MVU 路由过滤，UID 228 的 97 字符宏又会展开为长度动态的完整 stat_data；实际 token 必须抓真实请求体。

这张卡可以容纳大量条目，靠的是：

- CC V3 把所有条目作为标准的 character_book.entries 数组序列化进 JSON，没有使用神秘私有格式。
- 大多数详细知识不常驻，而是做成关键词叶子。
- 两个 EJS 路由条目用 getwi 把禁用条目当作可复用模块直接内联。
- 所有条目禁止递归扩散，避免 319 条互相点亮。
- MVU 用“当前状态 → 模型 → Patch → 下一楼状态”的反馈闭环维持长线进度。
- 远程配置助手同步切换界域总览、遭遇规则、随机正则和 MVU 所在界。

但它不是可以原样照抄的模板。最关键的问题是：

- 默认玄天的预路由静态源文本等价估算接近 4.9 万 token，而且 getwi 展开内容绕过原生世界书预算。
- 随机正则在人名被世界书扫描之后才运行，同一轮无法加载抽中角色的详细词条。
- 当前玄天低阶随机 NPC 正则本身也写错了 pattern，实际不会替换占位符；仙界低阶版本同样有误。
- 开局创建器、界域助手和状态组件都做整块 MVU 读改写，缺少事务与并发保护。
- 开局创建器写入字段不全，并把变量写在随后要删除的 UI 楼层上。
- 配置助手依赖精确名称并硬编码 319 条，扩卡、改名或局部失败都可能造成界域状态分裂。
- 当前通用拆包器虽然能帮助阅读，但直接回包会改变大量世界书元数据，不能作为发布流水线。

## 2. PNG 与角色卡载荷

### 2.1 容器结构

源 PNG：

- 文件大小：5,913,883 bytes
- SHA-256：d5fcf612f95620c285610a4702a18ffd0e98797e8903e2eaaf2cfb228a562752
- 5 个 PNG 块：IHDR、IDAT、tEXt、tEXt、IEND
- 全部 CRC 正确，IEND 正常结束，没有尾随数据

两个文本块分别使用 chara 与 ccv3 关键字。二者都包含同一份 Base64 JSON：

- 每份 Base64 文本：2,531,120 字符
- 解码后的原始 JSON：1,898,339 bytes
- 原始 JSON SHA-256：7759a56059d4e8bd17bfa6a09c5f2c45178393d703e5c5e523873eaa190757a8
- 规范化语义 SHA-256：8fff3e9f6fb8f042df3bed17fa1fb64499a129071a66039f3f1a670468b6de6f
- 规范：chara_card_v3，版本 3.0
- chara 与 ccv3 的解码字节和 JSON 语义完全一致

也就是说，PNG 为兼容性重复携带了两份同样的卡数据。这两份 Base64 共占约 5.06 MB，图像 IDAT 约 0.85 MB，正好解释了 5.91 MB 的总体积。

### 2.2 “超级大”主要由什么构成

权威 JSON 中的主要文本体量：

| 组成 | 字符或字节 |
|---|---:|
| 319 条世界书正文 | 210,144 字符 / 539,633 UTF-8 bytes |
| 17 条正则的替换文本 | 821,270 字符 / 959,372 UTF-8 bytes |
| 首条开场 | 18,650 字符 / 20,038 UTF-8 bytes |
| 4 个内嵌助手脚本 | 8,420 字符 / 9,366 UTF-8 bytes |

因此，文件体积上的“超级大”不只来自世界书。正则替换体中包含多个大型内嵌 UI，其中状态栏视觉代码与开局创建器占据了更大份额。世界书负责知识规模，UI 代码和双载荷复制负责相当一部分文件体积。

### 2.3 角色卡顶层

- 名称：《道渊》v5.3
- 嵌入世界书名：道友先上我断后
- 角色描述：297 字符
- personality、scenario、example、system prompt、post-history instruction 均为空
- 首条开场：18,650 字符
- 备用开场：1 条，内容是触发开局创建器的短标记
- 319 条世界书

- 4 个角色内嵌 Tavern Helper 脚本，全部启用

CC V3 的标准字段与顶层兼容镜像一致，没有发现 name、description、first message 等双份字段的语义分叉。

## 3. 无损解包与往返结论

### 3.1 解包覆盖

人工可读组件位于 components/unpacked：

- 世界书：319 条，249 个 txt、70 个 yaml
- 开场白：2 个文件
- 正则：17 条，其中 14 个替换文本文件、3 条空替换规则仅内联于状态文件
- 外置可读脚本：3 个远程加载器文本
- Zod：另从卡内脚本提取为 components/extracted-extensions/ZOD.ts

analysis/component-mapping.json 把每个组件关联回原 JSON Pointer、UID、名称和文件路径。最终完整性清单确认：

- 319 条世界书全部映射。
- 每条正文与权威 JSON 逐字符相等。
- 两个开场全部映射并相等。
- 17 条正则和 4 个脚本全部计入。
- UID 与条目名称均唯一。

### 3.2 真正无损的 PNG 回嵌

roundtrip/lossless-reembedded.png 将原始 JSON 重新写回 chara 与 ccv3，保留其余 PNG 块。结果与源 PNG 逐字节相同，PNG、JSON 与语义哈希全部复现。这证明当前自制 PNG 审计/回嵌链可以无损保存这张卡。

### 3.3 通用拆包器不能直接用于发布

通用 tavern-cards-forge 能将 319 条内容拆成可读文件，但本卡被识别为 mvu=false，Zod 也未建立独立声明。将拆包结果直接回包后，虽然仍有 319 条世界书、17 条正则和 4 个脚本，却产生 805 处语义差异：

- 302 条 extensions.depth 被改成 0，其中 301 条为 4→0、1 条为 2→0。
- 486 处 null 与数字 0 的类型变化，集中在 cooldown、delay、sticky。
- 11 个 selective 值改变。
- 4 个助手脚本的 export_with 元数据丢失。
- 开场白换行被规范化。

因此：

- decoded/payload-chara.raw.json 是本次审计的权威语义源。
- components/unpacked 适合阅读和编辑研究。
- 在修复字段保持与 MVU 检测之前，不能从 components/unpacked 直接生成公开发布物。

详细差异见 roundtrip/semantic-diff.json。

### 4.2 元数据分布

- enabled：295 true，24 false
- constant：54 true，其中 30 条当前常驻、24 条当前禁用
- selective：276 true，43 false
- 原始 position：after_char 281，before_char 38
- 实际 extensions.position：角色定义前 38，角色定义后 264，@depth 17
- insertion_order：310 条为 100；4 条为 200；2 条为 10；其余为 6、7、101 各 1
- extensions.depth：D4 302，D2 8，D0 4，D3 3，D1 2；只有 extensions.position 为 depth 的 17 条实际使用该值
- probability=100 且 useProbability=true：319 条
- group 全空：319 条
- secondary keys 全空：319 条
- vectorized=false：319 条
- ignore_budget=false：319 条
- prevent_recursion=true：319 条
- exclude_recursion=true：312 条
- scan depth、整词、大小写均继承宿主设置
- use_regex=true：319 条，但没有一个 key 使用 SillyTavern 的正则 key 语法

全卡 prevent_recursion=true 是规模控制的关键：一条世界书被送入上下文后，其正文不会继续触发另一批词条，防止人物简介中的地名、境界和势力名引发级联爆灯。

代价也很明确：知识不能靠原生递归自动联动；需要 EJS 或下一轮聊天文本才能补充更深层详情。

### 4.4 关键词叶子池

265 条已启用非 constant 叶子全部至少有一个主 key：

- 有效 key 出现 817 次，区分后的唯一 key 为 801 个。
- 每条最少 1 个 key，最多 23 个。
- 活跃叶子中有 13 组精确 key 被多个条目共享，例如南离火洲、中央神州、飞升、蛟龙、万魂殿。
- 许多境界与通用动作只用 2 至 4 个汉字，在普通叙事中很容易命中。
- 没有 group、secondary key、概率分流或状态条件帮助收窄同时命中的范围。

原始 319 条合计填写了 860 个 key、836 个唯一值。UID 13、14、285，以及禁用的 286 虽然是 constant，仍填写了 key；constant 条目不受这些 key 门控，当前启用的 13、14、285 实际始终注入。

这套设计适合“提到某人就加载某人”，但粗短词容易带来误亮灯。又因为 310 条都使用 order 100，预算不足时缺乏细粒度淘汰优先级。

原生激活、递归、预算和中文整词匹配语义可对照 [SillyTavern World Info 文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)。

### 4.5 当前界域之外的叶子没有被真正隔离

界域切换只同步：

- 两个 EJS 总览开关。
- 两个动态遭遇条目。
- 两组随机注入正则。
- MVU 的主角.所在界。

普通的仙界人物、地点、势力叶子并不会在玄天界模式下整体禁用，玄天界叶子也不会在仙界模式下整体禁用。因此，只要聊天文本出现另一界域的 key，仍可能跨界注入。它是“切换总览与随机池”，不是完整的界域知识隔离。

### 5.4 getwi 的真实语义

本机 ST-Prompt-Template 1.17.6.8 的实现确认：

- getwi 的首参为 null 时，在世界书上下文中使用当前角色绑定世界书。
- 第二参可按 comment、UID 或正则查找条目；本卡使用唯一 comment 精确查找。
- 它读取完整世界书后直接找首个目标，不以目标条目的 disabled 状态过滤。
- 对目标正文依次执行 World Info 正则、宏替换和递归 EJS，然后把原始结果内联。
- 找不到目标时只记录警告并返回空串，不会令整个生成失败。
- 它不是原生世界书激活，因此展开正文不受原生世界书预算截断。

当前阶段顺序是：

    SillyTavern 原生世界书先激活 UID 93
      → ST-Prompt-Template 在出站提示组装阶段执行 UID 93
      → getwi 顺序读取 10 个禁用模块
      → 展开内容进入最终提示

这正是它能把 10 个禁用条目当成一个“玄天界总包”的原因。相关实现与功能说明见 [ST-Prompt-Template features](https://github.com/zonde306/ST-Prompt-Template/blob/main/docs/features.md)。

### 5.5 这套 EJS 路由的优缺点

优点：

- 聚合包仍按普通世界书条目存储，作者可以在酒馆 UI 中查看和编辑。
- 禁用条目不会被原生绿灯重复激活。
- 切换只需启用一个路由条目，不必让模型看到两套大世界总览。
- 路由器短小，调度路径容易理解。

缺点：

- getwi 绕过原生预算，宿主的世界书 token 上限无法阻止聚合包膨胀。
- 依赖精确 comment；条目改名会静默变成空内容。
- 路由本身不读取主角.所在界，MVU 状态不能自动纠正错误开关。
- 远程助手逐项修改世界书、正则和 MVU，不是事务；局部失败可能四层不同步。
- 子模块 disabled 是防重复的隐含前提，误启用后可能重复注入。

## 6. 随机人物注入与同轮失效问题

### 6.1 八条随机正则

| 正则 | 当前 | 占位符 | 候选数 |
|---|---|---|---:|
| 玄天界低阶随机 NPC 注入 | 启用但 pattern 有误 | [RANDOM_NPC] | 41 |
| 玄天界高阶随机 NPC 注入 | 启用 | [RANDOM_NPC_HIGH] | 87 |
| 仙界低阶随机 NPC 注入 | 禁用且 pattern 有误 | [RANDOM_FAIRY_LOW] | 14 |
| 仙界高阶随机 NPC 注入 | 禁用 | [RANDOM_FAIRY_HIGH] | 25 |
| 玄天界绝色榜人物注入 1 | 启用 | [RANDOM_BEAUTY] | 103 |
| 玄天界绝色榜人物注入 2 | 启用 | [RANDOM_JUESE] | 103 |
| 仙界绝色榜人物注入 1 | 禁用 | [RANDOM_XUAN] | 34 |
| 仙界绝色榜人物注入 2 | 禁用 | [RANDOM_XIAN] | 34 |

UID 285 在玄天界模式下放入三个普通/高阶人物占位，UID 286 是仙界版本；UID 227 的变量规则还放入四种榜单占位。八个池共有 441 个候选位置、174 个唯一名字。

这里统计的是卡内候选池资产；由于两条低阶 pattern 本身无效，不能把候选数量误写成当前运行时实际抽取覆盖率。

175 个语义人物详情条目中，170 个可以被候选名字精确对应。五个断链点：

- UID 72 的候选省略了“长老”后缀。
- UID 151 的姓氏使用了“侯/候”不同字。
- UID 272 紫澪没有进入随机池。
- UID 290 的下划线与候选中的中点不一致。
- UID 318 虚渊没有进入随机池。

玄天两份榜单池内容完全相同，仙界两份也相同，但抽取是彼此独立的。协议要求两名不同角色，却没有无放回抽样；理论重复概率玄天约 0.97%，仙界约 2.94%。

还有一个与扫描时序无关的确定性正则错误：

- 规则 9 与 11 的 find 字符串缺少规范的起始斜杠。
- SillyTavern 1.17.0 的 regexFromString 会把末尾的 /g 当成模式正文的一部分。
- 因此当前启用的玄天低阶规则实际不会匹配 [RANDOM_NPC]；未来切到仙界后，低阶规则也不会匹配 [RANDOM_FAIRY_LOW]。
- 高阶规则 10、12 和榜单规则 13–16 的格式正常。

此外，UID 227 同时写着玄天与仙界四组 marker。界域切换只启用当前界的两条榜单正则，另一界 marker 会原样留在条件说明里，并不会被清理。

### 6.2 为什么同一轮拿不到抽中人物的详情

对 SillyTavern 1.17.0 的世界书与正则源码核查后，真实顺序是：

1. 先扫描聊天文本并确定世界书激活集合。
2. 完成世界书递归与预算处理。
3. 在最终提示组装阶段运行 World Info placement 的正则。
4. 正则才把占位符换成 random 宏，并最终选出名字。

因此，名字出现时，本轮世界书扫描已经结束。随机抽出的名字不能反向点亮对应人物详情。全卡又统一 prevent_recursion=true，没有第二条原生回扫通路。

实际结果是：

- 本轮模型通常只得到随机名字和聚合包里的粗略摘要。
- 如果模型把该名字写进聊天，且下一轮仍处于扫描深度内，人物详情才可能在下一轮加载。
- UID 285 要求“严格按人物身份、背景和性格”生成同轮遭遇，但其运行链并不能保证这一点。

这是源码可确定的时序缺陷，不需要依赖模型质量解释。证据见 [SillyTavern 1.17.0 world-info.js](https://raw.githubusercontent.com/SillyTavern/SillyTavern/1.17.0/public/scripts/world-info.js) 与 [SillyTavern 1.17.0 regex engine](https://raw.githubusercontent.com/SillyTavern/SillyTavern/1.17.0/public/scripts/extensions/regex/engine.js)。

### 6.3 本项目应怎样做

未来若要“随机抽人且同轮拿到详情”，应选择下面任一种：

- 在世界书扫描之前确定角色，并把名字写入可扫描的持久状态。
- 让 EJS 在选出名字后直接 getwi 对应人物条目，而不是期待原生世界书回扫。
- 为动态遭遇生成一个已经包含必要人物摘要的小型结构化包。
- 将随机角色选择放进受控脚本，再把“人物 UID + 必需详情”作为一次原子输出。

不能继续使用“世界书扫描后正则随机名字，再靠名字点亮详情”的链条。

## 7. MVU 与 Zod 完整解读

### 7.1 五个核心世界书条目

| UID | 名称 | 状态 | 职责 |
|---:|---|---|---|
| 227 | [mvu_update] | 启用、D0 | 变量含义、更新时机、数值规则与叙事约束 |
| 228 | 变量列表 | 启用、D0 | 用 format_message_variable 宏把当前 stat_data 送给模型 |
| 229 | [mvu_update]变量输出格式 | 启用、D0 | 强制 Analysis 与 JSONPatch 输出契约 |
| 230 | [mvu_update]变量输出格式强调 | 禁用、D0 | 更短的备用强调 |
| 231 | [initvar] 初始 | 禁用 | 初始 YAML 数据源 |

UID 231 虽然在原生世界书中禁用，却不是废条目。MVU-offline 初始化时会扫描已选中的全局、角色主世界书和附加世界书，按 comment 中的 [initvar] 识别数据源，不依赖条目的 enabled 状态。它支持裸 YAML、initvar 包裹与代码围栏，做宏替换后合并初始变量。禁用的意义是“不把初始化 YAML 当普通提示词发送”，而不是“不初始化”。

MVU 会在 initialized_lorebooks 中记录已初始化的世界书，避免重复装载。同名根对象的已有状态可在一级合并时整体遮住默认根，所以后来补挂世界书并不等价于对每个缺失子字段做深层补全。本卡两个开场都没有内联 initvar，实际初值来自 UID 231。

### 7.2 变量反馈闭环

    上一条有状态的消息楼层
      → MVU 复制或初始化 stat_data/schema
      → UID 228 把 stat_data 注入模型提示
      → UID 227 告诉模型何时更新
      → UID 229 要求输出 UpdateVariable + Analysis + JSONPatch
      → MVU 解析命令
      → Zod 对命令后的整棵状态做校验/归一化
      → 合法结果写入当前消息与当前 swipe
      → 下一轮继续

MVU 状态不是单一聊天全局对象，而是按消息楼层与 swipe 持久化。其数据含 stat_data、schema、display_data、delta_data、initialized_lorebooks 与 snapshot。系统寻找最近一个已有状态的上游楼层作为父状态，再把本轮更新写进当前楼层。

主要事件：

- GENERATION_STARTED 与 MESSAGE_SENT：确保变量初始化。
- MESSAGE_SENT 与 MESSAGE_RECEIVED：解析消息中的更新块。
- CHAT_CHANGED：重装当前聊天状态。
- MESSAGE_DELETED：延迟回放或修复删除后的变量链。
- 每 5 条接收消息做一次清理检查。
- 每 50 个更新保存快照，保留 20 个。

删除后的自动回放依赖历史消息中的 UpdateVariable 文本。创建器、状态栏和配置助手的直接 replaceMvuData 没有对应事件文本，因此从旧快照重演时不能保证恢复这些 UI 直写；它不是完整事件溯源。

### 7.3 Patch 方言

UID 229 称其“类似 RFC 6902”，但实际是 MVU 自有方言：

- replace：按路径 set
- delta：对数字做加减
- insert 或 add：向对象或数组插入
- remove：删除
- move：移动

解析器还兼容 YAML、JSON5、jsonrepair 后的 JSON，以及旧式 lodash 命令。

路径处理只做两步：去掉开头的斜杠，再把斜杠替换成点。它没有实现 JSON Pointer 的波浪号转义，也没有安全编码动态键。因此人物名、物品名或任务名如果包含点、斜杠、方括号等路径字符，可能被解释成另一层路径。这也是未来设计必须限制或转义动态键的原因。

UID 229 声称 path 不带开头斜杠会造成致命错误，但实际解析器把开头斜杠视为可选。这是提示契约与实现的另一处不一致。

### 7.4 Zod Schema 全字段树

卡内 Zod 脚本从未钉版本的远程 mvu_zod.js 导入 registerMvuSchema，然后在文档就绪时注册 Schema。

helper 会把 Schema 根改成 loose object，因此未知的一级根键可以保留；各嵌套 object 仍使用默认 strip，后续 Zod 全树校验会剔除嵌套对象中未声明的字段。

#### 世界

- 当前时间：string，默认“未知”
- 当前地点：string，默认“未知”
- 危机程度：string，默认“无”
- 遭遇冷却：number，可强制转换，异常回退 0，钳制到 0–15
- 动向：以事件标题为 key 的 record
  - 阶段：起、承、转、合之一
  - 类型：string
  - 地点：string
  - 描述：string
  - 兼容 type、description、desc、location、place、stage、phase 等英文键并归一化为中文

#### 主角

- 身份：姓名、性别、容貌、身形、衣着
- 修行身份：境界、宗门、宗门贡献、所在界
  - 所在界只允许玄天界或仙界
- 六项主要数值：生命、精血、灵力、修为、神识、道心
  - 除宗门贡献外，上述进度/状态数值按字段钳制到 0–100
- 神念：string
- 气运：动态 record
  - 类型、效果、使用状态、压制状态
- 灵根、状态：string
- 炼丹与炼器：
  - 阶级、熟练度、成功率、次数
  - 熟练度与成功率钳制到 0–100，次数只保证数字
- 储物袋：动态 record
  - 描述、数量
  - Schema 变换会剔除数量小于等于 0 的物品
- 功法：动态 record
  - 类型、境界、熟练度、描述
- 器物：动态 record
  - 等级、类型、损耗度、状态、描述

#### 道侣

动态 record，key 为姓名，每项含：

- 性别、种族、状态、境界
- 亲密、生命、灵力、修为、道心，均钳制到 0–100
- 性格、外观、身高、背景、神通、心声

#### 灵宠

动态 record，key 为姓名，每项含：

- 性别、种族、境界
- 生命、灵力、修为、亲密度，均钳制到 0–100
- 性格、容貌外观、神通、状态、心声

#### 人物

动态 record，key 为 NPC 姓名，每项含：

- 性别、头衔、境界
- 好感、生命、灵力、修为、道心，均钳制到 0–100
- 关系阶段、性格、描述

#### 机遇

动态 record，key 为任务名，每项含难度、目标、机缘、引言。Schema 只保留插入顺序最后 20 条。

#### 绝色榜

动态 record，key 为人物名，每项含排名、头衔、仙姿、群芳谱。Schema 没有数量上限；“每轮替换两名”只存在于提示协议。

#### 玉简

动态 record，key 为好友名，每项含：

- 性别、境界、关系、好感度
- 历史记录：以消息标识为 key 的 record
  - 发送者、时间、内容
  - Schema 只保留最后 100 条

#### $器灵台词

string 数组。该字段名前缀的美元符号是名字本身；Patch 路径必须保留。

### 7.5 Schema 的真实作用边界

Zod helper 在 MVU 命令链中工作：

1. 对当前完整状态做 clone。
2. 应用一条命令。
3. 对整棵状态 safeParse。
4. 成功才消费该命令并提交归一化结果。
5. 失败命令不提交；更新结束时未消费命令被清空，避免再由核心 MVU 重复执行。

但是，Tavern Helper 的 registerVariableSchema 只供变量管理器 UI 校验，代码层面的 replaceVariables 或 Mvu.replaceMvuData 是完全替换，并不会自动运行 Schema。官方说明见 [注册变量结构](https://n0vi028.github.io/JS-Slash-Runner-Doc/guide/%E5%8A%9F%E8%83%BD%E8%AF%A6%E6%83%85/%E5%8F%98%E9%87%8F/%E6%B3%A8%E5%86%8C%E5%8F%98%E9%87%8F%E7%BB%93%E6%9E%84.html)。

这意味着：

- 模型通过 MVU Patch 更新时，Zod 会参与。
- 开局创建器、配置助手或状态组件直接整块 replaceMvuData 时，不会立即补默认值、钳制或 strip 未知嵌套字段。
- 这些不合规状态会一直存在，直到以后发生会触发 Zod 的初始化或合法 MVU 命令全树校验。

Schema 的固定对象普遍使用 catch({}).prefault({})。如果整个世界、主角或炼丹对象被替换成错误类型，catch 可能令本次校验以空对象“成功”，而子字段默认值要到后续再次 parse 才补回。这是宽容容错带来的瞬时整段擦除风险。

### 7.6 UID 227 的更新规则

它把变量分为两组。

每轮强制判断或更新：

- 世界时间、地点、危机程度
- 遭遇冷却递减或重置
- 世界动向按起承转合推进
- 榜单人物轮换
- 玉简在有消息时追加
- $器灵台词替换

事件触发后更新：

- 主角的资源、受伤、修为、道心、库存、功法、器物、炼丹、炼器
- 道侣、灵宠与 NPC 的关系、状态、修为和境界
- 新机遇与完成、失败、放弃后的移除

规则还定义境界 DC、突破条件、修炼收益、道心区间、物品归零删除、功法熟练度、器物损耗、人物与道侣互斥等。它是一份“自然语言业务规则层”；Zod 只负责结构和部分数值边界，并不能验证大多数叙事约束。

### 7.7 UID 229 的输出协议

它要求每次回复末尾输出：

- UpdateVariable 外层
- 不超过 350 words 的 Analysis
- 15 类强制检查清单
- JSONPatch 数组

首次回复还要求模型从开局系统消息补齐姓名、性别、容貌、身形、衣着、境界 DC、灵根、功法、气运、宗门、神念、道心和修为。

这解释了开局创建器为何敢于不直接写全变量：作者把缺失字段转嫁给第一次模型更新。但这是提示词补偿，不是可靠初始化；模型漏写、Patch 失败或更新模型被关闭时，状态会继续残缺。

### 7.8 更新模型路由

全卡只有 UID 227、229、230 使用 [mvu_update] 标记，没有 [mvu_plot]。MVU-offline 可以把更新类内容交给额外模型，但标记并未覆盖全部相关词条：

- 普通剧情请求排除 update-only 内容。
- 额外更新模型仍可能接收其他激活但未标记的世界书。
- UID 228 的当前变量与部分叙事规则会按实际路由配置进入模型。

在当前 MVU 路由中，普通剧情请求会删除 update-only 条目，因此启用的 UID 227、229 不送给主模型；UID 228 没有该标记，仍会送给主模型。额外变量请求会保留同一世界书里其他已激活的普通 lore，且第一楼不做额外模型解析。

因此，它提供了更新模型能力，但提示分流并非完全隔离，token 成本仍需实测请求体确认。

## 8. 开局创建器：从备用开场到第一次生成

### 8.1 入口

第一开场是一段 18,650 字符的 HTML。按钮 switchToSecondGreeting 会：

1. 读取第 0 楼的 swipe。
2. 切换到备用开场的 swipe 1。
3. 若 API 不可用，则用 slash 命令发送一个触发文本。

备用开场只有一个短标记。角色正则 8“开局创造人物2”匹配该标记，用约 207,201 字符的 HTML/CSS/JavaScript 替换成完整创建器。

该创建器包含：

- 简单、普通、困难三种模式。
- 主角姓名、性别、种族、外观、身份、境界、灵根、功法、气运等字段。
- 可选道侣表单。
- 随机灵根与气运池。
- 浏览器 localStorage 存档、导入和导出。
- 远程图片、音乐与字体资源。
- Tavern Helper 与 MVU API 调用。

前端外观不在本报告范围内；以下只解读数据与副作用。

### 8.2 MVU 连接与即时写入

创建器启动时：

- 异步等待 waitGlobalInitialized('Mvu')。
- 成功后以当前消息楼层为 scope，调用 Mvu.getMvuData。
- 表单 blur 等事件会修改一个克隆，再用 Mvu.replaceMvuData 整块替换。
- 另有一个固定 800ms 的 initMvuDefaults。

关键竞态：800ms 到点时如果 mvuReady 仍为 false，该函数直接返回，之后没有重试。网络慢或 MVU 初始化慢时，默认写入永久跳过，而确认按钮仍可能继续执行。

### 8.3 独立世界书写入

确认时，创建器通过 legacy Tavern Helper API：

- 查询世界书列表。
- 如无“道渊开局创建人物”则新建。
- 为功法、气运和可选道侣逐条 createLorebookEntry。

本机 Tavern Helper 4.9.1 的消息 iframe API 确实暴露 getLorebooks、createLorebook、createLorebookEntry，所以在当前主机并非必然 ReferenceError。

但逻辑有三个问题：

- 新建世界书后没有把它绑定到角色、聊天或全局，正常情况下可能根本不进入提示。
- 每次确认都追加新条目，没有按固定 ID/comment 更新或清理，重复开局会累积重复记录。
- 世界书写入和 MVU 写入不是事务，前者成功、后者失败时不会回滚。

### 8.4 最终 MVU 写入

确认阶段直接写入：

- 主角境界、灵根、所在界、基础数值、气运等。
- 世界时间、地点、危机与动向。
- 其他动态集合清空。
- 可选道侣记录。

但它没有直接写：

- 主角姓名、性别、容貌、身形、衣着。
- 主角功法与宗门贡献。
- $器灵台词。
- 道侣性别。

主角表单本身没有身形与衣着输入；Schema 又没有主角种族、出身/身份，也没有道侣衣着与年龄字段。部分创建器信息只能留在系统消息中，不能无损进入 stat_data。

它还：

- 把主角.所在界硬写为玄天界。
- 给气运写入 Schema 不认识的“剩余次数”字段。
- 用一个不含遭遇冷却的世界对象覆盖整个世界。

由于直接 replaceMvuData 不触发 Zod，这些缺失和额外字段不会立即被自动修复。要等到后续 Zod 初始化或某次合法 MVU Patch 做整树校验后，才可能补默认、钳制或剔除。

### 8.5 第一次生成

创建器把主角与可选道侣资料拼成系统消息，然后执行一条 slash 管道：

    发送系统消息
      → /cut 当前 UI 楼层
      → /trigger 发起模型生成

UID 229 要求模型在第一次 JSONPatch 中从该系统消息补齐开局变量。也就是说，可靠性依赖：

- 系统消息没有被用户输入破坏。
- UI 楼层变量在删除前已正确继承到下一楼。
- 模型确实按首次初始化清单输出。
- Patch 解析和 Zod 校验成功。

创建器把未经转义的用户输入直接拼进带竖线的 slash 管道。若字段包含管道符或命令结构，可能改变后续命令边界。这里应当使用安全 API 或做严格转义，不能用自由文本拼接命令。

### 8.6 开局初始化的三组不一致

1. initvar 与 Schema：
   - UID 231 将遭遇冷却设为 20。
   - Schema 上限为 15。
   - 第一次 Zod 校验会把 20 钳制为 15。

2. 创建器与 Schema：
   - 创建器遗漏多个必需身份字段。
   - 气运多出未知字段，道侣少写性别。
   - 创建器覆盖世界时漏掉遭遇冷却。

3. 规则内部：
   - UID 227 要求世界动向最多 2 个。
   - UID 229 的强制检查要求维持 2–3 个。

这说明 Schema、initvar、创建器、更新规则和输出格式是分开手工维护的，没有单一真源。

### 9.1 MVU-offline

卡内只保存一行远程 import。固定 tag 对复现有利，但没有本地回退；远程加载失败时 Mvu 不存在，Zod、开局创建器、配置助手和状态组件均会降级或失败。

### 9.2 Zod helper

Zod helper URL 未钉 tag，二级 zod/v4/core 依赖也未钉。它与 MVU 初始化存在监听注册竞态：若脚本加载晚于初次 initialized 事件，首次校验可能错过，但后续命令 hooks 仍可工作。

其处理策略是“逐命令应用、整树校验、成功才消费”。更新结束后会清空未消费命令，防止无效命令再落到核心 MVU。

### 9.3 配置助手

界域切换按精确名称依次做四层同步：

1. 启停 UID 93 与 155 的 EJS 总览路由。
2. 启停 UID 285 与 286 的动态遭遇。
3. 启停玄天或仙界的四条随机人物正则。
4. 修改最后一楼 MVU 的主角.所在界。

变量模式切换还会同步：

- XML 状态栏条目与 MVU 的 UID 227、228、229。
- XML/MVU 对应状态栏正则。
- 名为 MVU 与 ZOD 的助手脚本。

它先写 localStorage，再逐步执行多个异步修改；每一步独立 catch，没有总事务或 rollback。任何中途失败都可能留下“界域总览、遭遇、正则、MVU 所在界”互不一致的状态。

脚本使用条目名称而不是稳定 UID 查找。改名后可能静默跳过。它还把“非数据库条目必须恰好 319 条”作为警告条件，扩展第 320 条就会触发不兼容提示。

模式切换不会 reload。把脚本树中的 MVU/ZOD 改成 disabled，主要影响下一次脚本生命周期；已经加载的全局 Mvu 与 Zod hooks 不会被这一步立即卸载。其父窗 runInParent 调用也没有 timeout，回传事件丢失时 Promise 和监听器可能长期悬挂。

开局创建器最终又把所在界硬写玄天界。如果用户此前通过助手选了仙界，可能出现 EJS 已是仙界而 MVU 被开局重置为玄天界的分裂。

### 9.4 Wiki

Wiki 使用两层脚本与一份索引：

1. 卡内 latest loader 从 Tavern Helper iframe 取得事件与聊天读取桥。
2. loader 向父窗口注入 daoyuan-term-widget.runtime.min.js。
3. runtime 拉取 schema 3 的 term-index/latest.json；2026-08-09 抓取时 sourceVersion=v53，共 292 条术语。

它只处理已经渲染的 assistant 消息 DOM：扫描 mes_text，给命中术语包 dao-term，点击后显示摘要、跳转或在允许域的 iframe 打开 Wiki。它不读 MVU，不写世界书、聊天源文本或模型提示。

它监听流式生成、消息渲染、编辑、swipe 与加载历史消息，并用 MutationObserver 补充重渲染；uninstall 会解除订阅、断开 observer 并拆除术语包装。

安全正项是链接、iframe 与 postMessage 都有协议、origin 和 allowlist 检查。但三层 URL 都使用 mutable latest。卡内第一层 dynamic import 没有 await/catch；首层或 runtime 失败可能产生未处理 rejection。索引失败会静默降级为“没有 Wiki”，主体聊天仍继续。对可复现发布而言，应固定版本和完整性，或将必要逻辑嵌入卡内。

本轮已经通过以下证据回答架构问题：

- 载荷与组件逐字节审计。
- 当前主机 API 和扩展版本核验。
- ST、TH、ST-Prompt-Template 与远程助手源码顺序。
- PNG 无损回嵌。

因此没有为了“多跑一次”而改变用户的现有酒馆。需要做后续行为验收时，应另建测试副本并明确允许导入、建聊、创建世界书和模型调用，再收集真实请求体、变量继承、同轮随机人物与删除楼层回放证据。

### 12.3 中风险一致性与维护问题

- initvar 冷却 20 与 Schema 上限 15 不一致。
- 世界动向上限在 UID 227 为 2，在 UID 229 为 2–3。
- 开局气运含 Schema 未声明字段，道侣缺性别。
- 创建器、Schema、initvar 和输出协议分别手写，没有单一真源。

- phone_data 与大量远程媒体随卡发布，增加隐私和外链失效风险。

## 13. 本项目未来“超级大卡”的推荐架构

### 13.1 保留的思想

应保留：

- 稳定 UID 与唯一逻辑名称。
- 公共规则、界域包、叶子知识、末端协议的分层。
- 人物、势力、地点、物品做细粒度叶子。
- 当前界域只装载一个聚合包。
- MVU 当前值、更新规则和输出协议形成闭环。
- 默认阻止世界书递归风暴。
- 真正发布前做 PNG、JSON、组件与运行时四层验证。

### 13.2 不照搬的实现

不要照搬：

- 用大量常驻自然语言规则堆到 4–5 万 token。
- 用 getwi 绕过预算却不单独计费。
- 依赖扫描后的随机正则去激活同轮详情。
- 用精确中文 comment 作为所有脚本的唯一外键。
- 让远程助手分四步修改状态且没有回滚。
- 让 Schema、initvar、创建器和更新规则各自维护一套字段。
- 直接把用户输入拼进 slash 管道。
- 对 MVU 状态做无序的整块并发 replace。
- 用 mutable latest 承担核心功能。
- 把用户个性化 phone_data 打进公开卡。

### 13.3 建议的单一真源

未来源目录应由一个 registry/manifest 驱动，至少声明：

| 字段 | 作用 |
|---|---|
| component_id | 永久稳定的机器 ID |
| display_name | 可改的中文显示名 |
| domain | 玄天、仙界、公共等作用域 |
| tier | 常驻、界域包、叶子、末端协议 |
| keys 与 secondary_keys | 激活条件 |
| position、depth、order | 提示位置与预算优先级 |
| dependencies | EJS、MVU、正则、脚本依赖 |
| writers/readers | 每个变量字段的写入者和读取者 |
| budget | 每个组件与展开包的 token 上限 |
| runtime_contract | 需要的扩展、版本与失败策略 |

由这一份 registry 生成：

- CC V3 世界书条目。
- EJS 路由表。
- 配置助手的开关集合。
- 随机池。
- Schema、initvar 与创建器默认值。
- 依赖账本和验证器断言。

任何改名、增删和界域迁移都应在构建时检查，不在运行时靠“正好 319 条”猜测。

### 13.4 推荐运行分层

    L0 最小公共内核
       时间、合理性、叙事边界、最小 MVU 协议

    L1 当前界域包
       地理骨架、势力摘要、等级与经济
       必须独立计入预算，不能隐形绕过

    L2 关键词叶子
       人物、地点、势力、物品
       采用主 key + 二级 key + realm 条件

    L3 当前场景包
       由脚本或 EJS 原子选择本轮必要角色与地点
       需要谁就直接带谁的最小详情

    D0 状态与输出
       当前变量、更新规则、严格输出格式

公共内核应设置硬 token 上限；界域包、场景包和叶子分别计数。构建失败要显示“哪一层超预算”，而不是让 getwi 隐形增加上下文。

### 13.5 推荐 MVU 方案

- Schema 是唯一字段定义源。
- initvar 从 Schema 默认值生成。
- 创建器表单与提交 payload 从同一类型定义生成。
- 更新规则引用字段 ID，不手写多份路径。
- 对动态 record key 做禁止字符或标准编码。
- 所有外部写入走一个串行写队列；至少比较基准版本，避免末写覆盖。
- 界域切换作为一个事务计划：预检全部对象，全部成功才提交，否则恢复旧状态。
- 不把初始化状态写在马上删除的消息楼层。
- 开局创建世界书必须显式绑定、使用稳定条目 ID，并支持更新/清理。
- 首次模型更新只负责叙事增量，不能承担基础字段补齐。

### 13.6 推荐随机人物方案

随机选择应输出结构化结果：

    realm
    selected_character_id
    selected_character_name
    required_component_ids
    cooldown_after_selection

然后在同一阶段直接装载 required_component_ids。人物显示名可以改，机器 ID 不能改；候选池应由人物 registry 自动生成并验证 100% 覆盖。

### 13.7 推荐依赖与发布策略

- 核心运行代码固定 tag 或 commit。
- 保存当前获取内容的 SHA-256 与许可证/来源。
- 对关键能力提供本地嵌入或可控镜像。
- mutable latest 只用于非关键增强，并要 await、catch 和降级提示。
- 发布前清除用户运行数据、邮箱样例、聊天联系人和私有媒体。
- 每次构建做源组件 → JSON → PNG → 再解码的语义 parity。
- 真机验收覆盖导入、新聊、开局、第一次生成、连续多轮、界域切换、随机人物、删除/重生成、断网与回归。
