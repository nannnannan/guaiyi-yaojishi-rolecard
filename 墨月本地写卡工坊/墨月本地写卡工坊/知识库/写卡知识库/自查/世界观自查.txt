世界观自查标准

本文件供AI在完成世界观创作后自动审查使用。
根据世界观类型（路径A/B/C）和是否使用MVU+EJS，执行不同深度的检查。

═══════════════════════════════════════
一、通用检查（所有路径都要做）
═══════════════════════════════════════

1. 信息密度检查（核心重点！！！）

世界观是信息密度最高的提示词。核心原则：用极致的字数说清所有设定。
不删任何核心要素，但也不留任何一个无用的词。
世界观不需要写出宏大的感觉，只需要精准与完整。

1.1 冗余表达压缩
逐句检查，每个句子是否能更短：
- "这是一个剑与魔法的世界" → "剑与魔法世界观"
- "在这个世界中，存在着五种元素" → "五种元素：火、水、风、土、雷"
- "修炼者需要通过不断的修炼来提升自己的境界" → "修炼提升境界"
- "世界由三大帝国统治，分别是..." → "三大帝国：A、B、C"
- 所有"是一个""存在着""分别是""需要通过""由...组成"等连接词 → 用冒号、逗号或直接列举替代

1.2 句式结构检查
- 有无"的"字滥用？（"强大的魔法师的组织" → "强力法师组织"）
- 有无多余的主语？（"该组织拥有..." → 直接写属性）
- 有无重复描述？（同一信息在不同地方出现两次）
- 有无可以合并的短句？（将多个一两词的行合并为一行）
- YAML键名本身能说明的，值里不要重复（键是"力量体系"，值不要再写"本世界的力量体系是..."）

1.3 废话检查
- 是否写了模型训练数据中已有的常识？- 真实背景（路径A）：不写"日本是岛国""唐朝有科举"等
  - 泛概念（路径B）："剑与魔法世界有冒险者"等AI已知的套路
  - 原创世界（路径C）：此项不适用，原创内容必须写清楚
- 判断标准：删掉这句话，AI是否还能正确表现？能删就删

1.4 完整性检查（与压缩同等重要！）
- 压缩不是删除核心设定！
- 每个独特的设定要素是否都保留了？
- 压缩后是否丢失了关键信息？（如：把"金丹期可御剑飞行，元婴期可神识外放"压缩成"修炼提升境界"→信息丢失，不可接受）
- 标准：另一个不了解你世界观的AI，只看这份条目，能否完整还原你的世界设定？

2. 绝对零度与白描检查

2.1 绝对零度原则
- 有无主观评价？（"强大的""神秘的""令人畏惧的"→ 删除）
- 有无抽象修饰？（"宏伟的宫殿"→ "占地三百亩的宫殿"）
- 有无比喻和意象？（"如同天堑"→ "宽三百丈的裂谷"）
- 有无感叹和评论？（"令人叹为观止"→ 删除）

2.2 白描原则
- 不用形容词堆砌
- 一个设定一句话说清楚
- 能用名词和动词说清的不用形容词

3. 结构清晰度检查
- 是否YAML格式？
- 层级是否合理（不过深也不过浅）？
- 同类信息是否归类在一起？

4. 条目配置检查

4.1 递归设置
- 所有条目是否都勾选了"不可递归"和"防止进一步递归"？
- 无论蓝灯还是绿灯都必须勾选

4.2 位置设置
- "大"世界观（世界总纲、区域速览、背景设定）→ 角色定义前
- "小"世界观（势力详情、NPC、事件、EJS控制器）→ 角色定义后
- 没有条目放在D1~D999（除MVU相关条目外，D0以外不放东西）

4.3 顺序设置
- 世界总纲：顺序1
- 区域速览/背景设定：顺序2-3
- 角色速览：顺序4
- 场景/事件详情：顺序50-98
- 核心角色详细信息：顺序99
- NPC/EJS控制器：顺序100

═══════════════════════════════════════
二、路径A（真实背景）专项检查
═══════════════════════════════════════

1. 极简性检查（路径A的核心）
- 条目是否只包含用户自定义的额外设定？
- 是否删除了所有模型已知的信息？
- 参考标准：如果AI的训练数据里已经有，就不该出现在条目中

2. 条目数量检查
- 路径A通常只需要1个蓝灯条目
- 如果超过1个条目，确认是否真的有必要拆分

3. 触发配置
- 应为蓝灯常驻
- 位置：角色定义前，顺序1

═══════════════════════════════════════
三、路径B（小世界）专项检查
═══════════════════════════════════════

1. 自定义内容完整性
- 核心规则是否说清楚了？（力量体系、社会结构等）
- 与AI已知概念的差异是否明确标注？（如"本世界没有龙""魔法不需要吟唱"）
- 关键名词是否都有解释？（自造词、专有名词）

2. 条目数量检查
- 小世界通常1-3个蓝灯条目就够
- 如果拆分了很多绿灯条目，考虑是否已经属于大世界

3. 触发配置
- 主体设定应为蓝灯常驻
- 位置：角色定义前，顺序1

═══════════════════════════════════════
四、路径C-方案一（传统条目拆分）专项检查
═══════════════════════════════════════

1. 条目拆分合理性
- 世界总纲是否只包含一段话概括 + 大区域名称列表 + 核心规则极简版？
- 区域速览是否只列了区域基本信息和势力名字（不展开细节）？
- 每个势力/场景是否独立一个条目（不混在一起）？
- 是否有条目过大需要进一步拆分？（单条目超过800token建议拆分）

2.蓝灯/绿灯分配检查
- 世界总纲 → 蓝灯
- 区域速览 →蓝灯
- 势力/场景详情 → 绿灯
- NPC → 绿灯
- 事件类型 → 绿灯

3. 绿灯关键词检查（重点！）
- 每个绿灯条目是否设置了关键词？
- 关键词是否用英文逗号","分隔（不是中文逗号"，"、不是空格）？
- 关键词是否覆盖了所有可能的称呼方式？- 势力条目：全名,简称,所在地名（如：天剑圣地,天剑峰,天剑）
  - 场景条目：场景名,别称,所在区域名（如：红尘酒家,酒家,红尘）
  - NPC条目：全名,昵称,外号,职务（如：林小雨,小雨,班长）
- 同一角色/势力的多个条目，关键词是否一致？
- 是否有遗漏的别名/昵称/简称？

4. 条目层级配置检查
- 第一层（世界总纲）：蓝灯，角色定义前，顺序1
- 第二层（区域速览）：蓝灯，角色定义前，顺序2-4
- 第三层（势力/场景详情）：绿灯，角色定义后，顺序50-98
- 第四层（NPC详情）：绿灯，角色定义后，顺序100

5. 内容层级一致性
- 总纲只写概括，不写细节
- 速览只列名称，不展开描述
- 详情才写完整信息
- 检查是否有细节泄漏到上层（如总纲里写了某个NPC的详细背景）

═══════════════════════════════════════
五、路径C-方案二（EJS+MVU联动）专项检查
═══════════════════════════════════════

⚠️ 重要提醒：EJS+MVU方案涉及变量结构脚本、EJS代码、多个世界书条目的联动，
检查内容非常多。强烈建议用户新开一个聊天栏，专门进行此项自查。
在新聊天中说"帮我自查EJS+MVU世界观系统"即可。

---

5.1 条目状态检查

- 世界总纲/区域速览 → 蓝灯常驻（同方案一）
- 被EJS控制器动态加载的条目（势力/事件/NPC详情）→ 必须设为禁用（enabled: false）
  - 禁用的条目不会自动发送给AI，只有EJS控制器通过getwi()调用时才加载
  - 如果手动开启这些条目，会导致所有设定同时出现在AI上下文中，适得其反
- EJS控制器本身 → 蓝灯常驻，角色定义后，顺序100

5.2 EJS控制器代码检查

结构检查：
- 是否以@@preprocessing开头？（必须）
- @@preprocessing是否不和@@generate_before/@@generate_after同时使用？
- 是否在读取变量前用typeof防重复声明？正确：if (typeof xxx === 'undefined') var xxx = getvar('stat_data.xxx');
  错误：const xxx = getvar('stat_data.xxx');
- 所有getwi()调用是否都加了await？
  正确：<%- await getwi('条目名') %>
  错误：<%- getwi('条目名') %>
- 读取MVU变量时路径是否以stat_data.开头？
  正确：getvar('stat_data.世界.当前地点')
  错误：getvar('世界.当前地点')

逻辑检查：
- 是否根据地点/区域变量加载了对应区域条目？
- 是否根据在场角色变量加载了对应角色条目？
- 是否根据当前事件变量加载了对应事件条目？
- 角色别名映射是否完整？（所有角色的昵称、简称是否都在aliasMap中）
- 是否同时检查了变量中的角色和用户消息中提到的角色？
- 是否有跳过第0楼（开局消息）的逻辑？

加载覆盖检查：
- 列出所有被禁用的条目名，逐个检查EJS控制器中是否有对应的getwi()调用
- 是否有条目被禁用但EJS控制器中没有对应的加载逻辑？→ 该条目永远不会出现
- 是否有条目名在getwi()中拼写错误？

5.3 MVU变量与EJS联动检查

变量结构中是否有支撑EJS控制器的字段：
- 当前地点/区域相关变量 → 支撑地点判断
- 在场角色相关变量 → 支撑角色加载
- 当前事件相关变量 → 支撑事件加载
- 如果EJS控制器引用了某个变量路径，该路径在变量结构脚本中是否存在？

变量更新规则检查：
- 地点变量的check规则是否能确保场景切换时及时更新？
- 在场角色变量的check规则是否能确保角色进出场时及时更新？
- 事件变量的check规则是否合理？

5.4 MVU子系统完整性检查（交叉引用MVU自查）

以下检查应参照"自查/MVU自查"执行完整检查，这里仅列出关键项：

变量结构脚本：
- 头尾是否原封不动（import registerMvuSchema / $(() => { registerMvuSchema(Schema); })）？
- 是否使用了zod 4语法（prefault而非default，transform而非min/max）？
- 是否没有import z或_？
- 是否没有使用.strict()或.passthrough()？
- 变量名是否有繁体字？→ 必须改为简体

初始变量：
- 条目名是否为[initvar]变量初始化勿开？
- 条目是否为禁用状态？
- YAML格式是否正确？
- 初始值的类型是否与变量结构一致？
- 地点/区域/在场角色等初始值是否与开局消息场景一致？

变量列表：
- 条目名是否为"变量列表"（不加[mvu_update]）？
- 内容是否为固定格式（{{format_message_variable::stat_data}}）？
- 位置是否为D0/D1，顺序200？

变量更新规则：
- 条目名是否包含[mvu_update]前缀？
- 是否对世界观相关变量（地点、在场角色等）写了合理的check规则？
- type定义是否与变量结构脚本一致？

变量输出格式：
- 条目名是否包含[mvu_update]前缀？
- 内容是否为固定格式（参考MVU自查中的完整模板）？
- 位置：Gemini设D0 / Claude设D4？

5.5 正则配置检查

MVU正则（三个）：
- [不发送]去除变量更新：仅格式提示词，替换<UpdateVariable>为空
- 变量更新中/完整变量更新：仅格式显示，美化或折叠显示
- 是否三个正则都已导入？

如果使用了<StatusPlaceHolderImpl/>界面占位符：
- [不发送]界面占位符：仅格式提示词，替换为空
- [界面]状态栏：仅格式显示，替换为界面代码

═══════════════════════════════════════
六、整体联通性检查
═══════════════════════════════════════

1. 开局消息一致性
- 开局消息的场景是否与世界观设定一致？
- 如果有MVU，开局消息场景是否与初始变量一致？
  - 初始变量里"当前地点=教室"，开局消息里角色是否在教室？
  - 初始变量里"在场角色=白娅"，开局消息里白娅是否在场？
- 如果有多个开局，每个开局的<initvar>是否与该开局场景匹配？

2. 名称一致性
- 世界观条目中的势力名、地名、角色名等，在所有条目中拼写是否一致？
- 关键词中的名称与条目内容中的名称是否一致？
- EJS控制器中getwi()的条目名是否与实际条目名完全一致（包括空格、标点）？
- 变量结构中的地点名、角色名是否与世界观条目中一致？

═══════════════════════════════════════
通用自查原则
═══════════════════════════════════════

1. 只检查结构和格式正确性，不检查世界观创意本身
2. 如果正确就说正确，不要为了检查而找问题
3. 给出具体错误位置和修正方案
4. 发现错误时直接输出修正后的完整代码/内容
5. 路径C-方案二的完整检查工作量大，建议新开聊天栏专门进行
