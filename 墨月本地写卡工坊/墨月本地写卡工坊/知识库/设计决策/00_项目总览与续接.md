# 项目总览与续接

更新时间：2026-08-26

## 哥哥明确提出的需求

- 项目是长线、复杂任务，需要边了解边留下可续接记录。
- 需要设计三种写卡器：酒馆预设、Zeabur Web、本地 IDE/Codex 写卡环境。
- 新体系以“生境人设写卡”为重要基础，旧版将彻底重构。
- 酒馆预设只附带两种交互：WTC agent 式脚本、传统酒馆一问一答脚本。
- Web 端不受酒馆环境限制，最终能够导出 PNG 角色卡，并为世界书、开场白等提供更方便的可视化编辑。
- 本地环境类似现有“青空莉”式工程，但聚焦写卡、MVU、EJS 和脚本；需要把 Skill、AGENTS、必读资料和工作逻辑设计好。
- 本轮优先完成酒馆纯对话、酒馆 WTC Agent 与 Web Agent 共用的破限和专项装配内核；本地 IDE/Codex 环境不需要破限层。
- 旧破限不要求保留，目标是从底层重写并超过旧版；设计全部完成后再整体迁移，不在旧预设上持续打补丁。
- 专项任务采用手动装配：只有开启的专项条目才通过变量把完整任务合同交给小COT，未开启功能不默认召回。
- 当前酒馆版改用位于提示词末端的 User 路由，模型自行进入预设可见思维；新预设不使用assistant预填、noass、停止字符串或消息压缩。尾部源自A04机制并已改写为写卡工坊语义，必须重新实测。
- Web 架构不预设 Vue，优先选择长期维护和使用更方便的方案。
- 可以读取 `C:\Users\三明月\Desktop\三明月` 内现有环境与教程。
- 调色盘和旧教程属于历史资料，只能提供思路，不能直接当成新方案。

- 普通模式不设计或生成正则；MVU与状态栏需要的清洗、匹配和安装统一由用户另行提供的正则文件负责。

## 当前判断

- 三个产品不应各自维护一套互不相干的写卡知识；更合适的方向是共享“写卡核心规范 / 角色卡数据模型 / 导出规则”，再为酒馆、Web、本地 IDE 分别提供适配层。
- 生境规范应只决定“角色内容如何形成”；传统问答和 WTC agent 应是两套交互适配器，不应各自复制一套人设知识。
- 酒馆端应从同一份规范源生成两个独立装配版本，而不是让纯对话版残留 WTC 工具名、虚拟路径和写入承诺。
- 酒馆纯对话版的常驻头部、专项变量、User尾部、自定义COT、小单元构建与六条清洗正则已经重新落地；真实预设迁移与酒馆实机仍未完成。
