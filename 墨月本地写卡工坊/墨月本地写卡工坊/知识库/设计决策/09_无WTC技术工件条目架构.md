# 无 WTC 技术工件条目架构

更新时间：2026-08-26

状态：完成当前规则、类型定义、初始模板、知识库与旧写卡器的交叉核对；当前已建立九个MVU条目、两个普通消息前端条目和两个单角色多阶段人设EJS条目。普通模式不设置正则条目，清洗、匹配与安装统一使用用户另行提供的正则文件；旧预设尚未迁移。

## 一、本阶段的准确目标

本阶段只设计在 SillyTavern 酒馆中直接对话、由用户复制结果使用的技术写卡条目，不使用 WTC，不承诺读取文件、写入世界书、创建脚本、执行构建或自动验收。

EJS与前端专项可以按实际需要直接开启。MVU链固定为“初始变量设计 → 初始变量格式化 → 变量规则设计 → 变量规则格式化 → 变量结构脚本 → MVU固定输出 → 状态栏需求判定 → 原生HTML或单HTML Vue创作（二选一）”。EJS多阶段人设固定为“单角色设计 → 单角色创作”，普通模式不设计或生成正则。

最终交付不是教程摘要，而是可直接复制的完整技术工件。讨论、需求确认、示例、检查过程、安装说明与最终代码必须彼此分离。

## 二、资料优先级与已经发现的冲突

新技术条目的事实来源按以下顺序使用：

1. 当前 `@types` 接口定义与 `.cursor/rules` 规则。
2. 当前项目的 `初始模板` 与可运行示例。
3. `写卡知识库` 中仍与当前接口一致的知识。
4. 旧写卡预设中的需求引导与用户沟通经验。

旧资料不能整份直接塞进新条目，原因不是风格问题，而是其中存在会让成品实际出错的冲突：

- 旧 MVU 前端主要输出单文件 HTML；当前本地工程模板则使用 `schema.ts + 注册脚本 + Vue/Pinia store + 独立前端文件`。两种交付环境不同，不能在一份代码中混装。
- 本阶段目标是酒馆直接复制，不是本地工程。因此 Zod 最终工件采用可直接放入角色脚本的注册版；本地工程中的纯 `schema.ts` 结构留给未来 IDE/Codex 版。
- `getAllVariables()` 在当前 iframe 类型定义中仍然有效，可以用于酒馆内直接安装的显示界面；但必须从 `stat_data` 下读取 MVU 数据，不能使用旧资料里省略路径核对的自由写法。
- 当前本地资料对 `Mvu.events.COMMAND_PARSED` 的监听参数存在冲突：规则和类型注释使用 `commands =>`，类型映射与另一份知识条目却声明 `(variables, commands, message_content) =>`。正式生成涉及此事件的代码前，必须按用户实际安装的 MVU 版本确认或实测，不能任选一个示例照抄。
- 当前初始模板的变量列表标签是单数 `<status_current_variable>`，旧知识库和旧写卡器却使用复数 `<status_current_variables>`。新版固定正文必须取当前初始模板，不能让两套标签随机出现。
- 旧 EJS 模板把 `getwi(null, '条目名')`、固定函数白名单和“模板外一律拒绝”写成铁律；当前知识资料支持按条目名读取、指定世界书、变量操作、注入与预处理等更完整能力。新版应按实际功能限制，不用旧模板人为砍掉能力。
- 旧前端资料大量使用 `innerHTML` 拼接模型输出。酒馆界面是无沙盒 iframe，未经转义的模型文本不能默认作为 HTML 执行；新版必须优先使用文本节点、jQuery `.text()` 或明确的白名单解析。
- 旧资料把“所有注释只能使用 `/* */`”作为通则。新版改为按真实工件语法选择合法注释，不再制造不存在的平台限制。

因此，新条目不会把现有知识库原文整包注入，而是从当前规则中重新提炼小型知识胶囊。

## 三、建议的正式条目结构

### 3.1 MVU 基础变量系统：五个自定义步骤加固定输出

变量结构脚本不是上游设计源，而是最终编译产物。若先生成Schema，再讨论初始变量，任何字段、层级、空集合或权限调整都会迫使用户返工前置脚本。现在的原则是：先完成初始变量与更新规则两个完整包，最后一次性生成结构脚本；一个格式化条目仍然只生成一个真实技术文件。

#### 第一步：`🌱 MVU·初始变量设计`

同时确定玩法真正需要保存的字段和开局状态。终稿必须保留最终字段名、含义、消费者、数据形态、固定/动态结构、空集合项目类型、结构约束、权限和初始值，形成唯一`<MVU初始变量设计终稿>`；不写YAML、Schema或正式更新规则。

#### 第二步：`🧾 MVU·初始变量格式化`

只消费完整初始变量设计终稿，生成一个`[initvar]变量初始化勿开`YAML及配置。initvar只保存实际开局数据；YAML无法表达的结构语义继续由设计终稿保存，供后续规则与Schema生成使用。

#### 第三步：`⚖️ MVU·变量规则设计`

消费完整初始变量设计终稿与initvar，筛选哪些可更新字段确实需要专门规则，并讨论触发、保持、知情、幅度、动态集合操作和复合一致性。若讨论暴露字段、类型、权限或初值错误，返回第一步重做终稿与initvar，不在规则中补丁式改结构。

#### 第四步：`📐 MVU·变量规则格式化`

消费初始变量包与变量规则设计终稿，生成一个`[mvu_update]变量更新规则`YAML及配置。它负责同规则固定字段合并、动态键类型、对象嵌套、类型和路径核对；不补造玩法规则，不列只读字段，也不输出JSON Patch命令。

#### 第五步：`🧬 MVU·变量结构脚本`

消费完整初始变量包与变量规则包，直接生成一个Zod 4变量结构注册脚本，不进行讨论。两个包各包含语义终稿和正式YAML，避免从空`{}`、空`[]`、单个枚举初值或缺省规则中猜类型。脚本必须接受当前initvar，并能表达已确认的更新操作。

#### 第六步：`📎 MVU·固定输出`

原样输出不随角色卡设计变化的MVU世界书内容与配置：当前模板的单数`<status_current_variable>`变量列表和`[mvu_update]变量输出格式`。固定输出不读取任何设计终稿，不进行创作型讨论，也不得输出正则；完成后直接进入状态栏需求判定。

### 3.2 MVU状态栏

#### `🧭 MVU·状态栏需求判定`

面向不懂代码的新作者，把用户对状态栏的大白话转换成可实现的显示、资源、布局、交互、移动端和失败表现；严格区分普通酒馆模式可承接、需提供外部资源与应转IDE的需求，并在原生HTML和单HTML Vue之间选择唯一路线。头像、立绘、背景等图片必须先取得真实公开`https://`地址，普通模式不让创作条目临时猜酒馆头像接口。需求确认后必须重新索取一次最新完整初始变量材料，再从头核对路径、类型、动态结构和开局状态，最终形成自足的`<MVU状态栏创作合同>`。本条目不编写代码。

#### `🪶 MVU·原生状态栏创作`

只消费指定原生HTML路线的完整创作合同，不承接聊天。它使用固定的MVU读取、刷新、`textContent`与`data-mvu-*`绑定骨架，只生成固定DOM和CSS，适用于固定字段、简单进度与原生折叠；不得追加自定义业务JavaScript。

#### `🧩 MVU·Vue状态栏创作`

只消费指定单HTML Vue路线的完整创作合同，不承接聊天。它使用酒馆助手iframe的全局Vue与固定挂载、读取、刷新、安全函数骨架，只生成Vue模板、CSS和最小本地界面状态；禁止SFC、import、CDN、Pinia、Router、双花括号插值、`v-html`与构建工具。

普通模式至此停止。`<StatusPlaceHolderImpl/>`的匹配、MVU清洗和状态栏安装统一由用户提供的正则文件负责，不再设置相应设计或格式化条目。

### 3.3 EJS 区

EJS基础版只承接一个明确用途：依据现有MVU变量为一个角色切换多阶段人设。旧式“蓝灯控制器调用多个禁用阶段条目”不再使用；所有阶段正文直接放在同一个蓝灯EJS条目中，借此删除`getwi`、禁用条目名称、跨条目加载与重复声明等失败点。

#### `🧭 EJS·多阶段人设设计`

职责：一次只与用户讨论一个角色。消费最新完整`[initvar]变量初始化勿开`、`[mvu_update]变量更新规则`、该角色稳定人设和用户的阶段构想，判断多阶段人设是否必要，选择最少的现有阶段变量，形成互斥且穷尽的条件表，并只写各阶段相对稳定人设的差异。

用户一次提供多个角色时必须先选一个；完成一个角色的最终提示词后，保存并隐藏本次全部楼层，再从干净上下文重开本条目处理下一个。待定方案确认后必须重新收集一次最新initvar和更新规则，最后一次材料作为唯一事实来源。最终工件是一份自足`<EJS多阶段人设创作提示词>`，本条目不生成EJS代码。

#### `⚙️ EJS·多阶段人设创作`

职责：只消费一份完整创作提示词，生成一个角色的一份EJS代码和一份世界书配置。代码只通过`getvar('stat_data.路径', { defaults: 初始值 })`读取合同列出的变量，使用一条`if / else if / else`链，每轮只输出一个角色专属标签包裹的阶段差异正文。

本基础版明确禁用`getwi`、`activewi`、变量写入、聊天读取、动态激活、注入、正则、装饰器、外部脚本和网络请求。EJS小COT注释只使用`<%# @qk-unit | ... %>`；最终配置固定为启用的蓝灯常驻、角色定义之后、order 1—8内已确认值、双向禁止递归和概率100。

### 3.4 前端美化区

#### `🧭 前端·需求与实现方案`

职责：与不懂代码的新作者持续收集白话需求，完成页面类型、出现条件、与正文关系、最小运行时输出协议、信息层级、资源、交互、移动端、失败表现和酒馆能力边界判断，最后编译一份自足`<前端创作合同>`。本条目不生成代码。

正文美化与结构化页面不再拆成两个互斥聊天入口。二者共用同一判断流程：自由文本只保留一个外层标签；需要固定位置、重复项目或条件区块时才设计最浅结构化协议。用户不需要先知道自己属于哪一类。

全部平台知识只放在本聊天条目：当前楼层消息读取、标签与字段协议、文本安全、iframe布局、资源URL、可选发送行为、风险与IDE分流。需求完成后先交付待确认方案，确认并复核后再输出合同；创作条目不继续读取接口教程或需求示例。

#### `🎨 前端·正式创作`

只消费完整前端创作合同，不承接聊天、补需求或换技术。一次交付两个彼此严格映射的工件：运行时输出规则正文与完整HTML；世界书配置放在代码块外，普通模式不生成正则。

创作条目不携带接口知识、教程和预设示例，只保留合同执行、双工件映射、小COT代码注释和静态核对纪律。合同缺少标签、字段、接口、资源、交互或失败表现时直接退回需求条目，不临场猜测。

两份工件在同一回复中完成，是因为它们共享唯一标签和数据协议，分开创作反而增加字段漂移；它们必须使用两个独立代码围栏，HTML未闭合前不得跳出解释。普通模式的正则仍由用户提供的统一文件负责。

## 四、技术条目的统一输入合同

MVU流水线不把交谈与格式化混在一起：初始变量和更新规则各有独立设计终稿，也各有只生成一个YAML的格式化条目；变量结构脚本只在两包完成后编译一个脚本；固定输出只交付MVU正文。状态栏需求判定独占全部聊天并编译自足合同，两个互斥创作条目只接受合同并一次生成。普通模式不设计或生成正则，清洗与安装统一交给用户提供的正则文件。

当前前端双条目、MVU状态栏链与EJS双条目都只负责新建设计和生成；修复现有工件需要另定边界。EJS专项独立开启，不能被前端合同顺手召回。

条目必须先判断以下四件事：

1. 当前运行环境是不是酒馆直接复制版。
2. 当前唯一工件是什么。
3. 它依赖的上游工件是否已完整提供。
4. 本轮处于讨论、确认、构建还是修复阶段。

不属于当前工件的资料原样切出，请用户保存后到对应专项处理。不能为了“完整方案”主动加载未开启的技术模块。

## 五、交谈与严格代码工件的小 COT

### 5.1 开头任务寄存器

所有技术专项共用七行任务寄存器，明确本轮输入、专项与状态、事实基线、常驻规则与专项知识、当前单元、边界与验收、输出与停止。它不会在代码前预演完整文件。

依赖缺失时，任务寄存器进入dialogue或blocked；关闭thinking后只提出一个问题或报告第一个真实阻断点，不输出猜测代码。

初始变量设计的小COT同时完成变量取舍、结构语义和开局值，但不预演技术文件；变量规则设计只消费已经落地的初始变量包，不改变上游结构。EJS设计条目只形成单角色创作提示词，正式创作条目只编译单个蓝灯条目。它们都不在讨论轮维护不断变形的代码草稿。

initvar与更新规则格式化只转换各自终稿；最终变量结构脚本先核验四份输入，再只生成一个脚本。MVU固定输出只核对模板正文；状态栏需求判定只形成创作合同；原生HTML与Vue创作条目各自只处理一种互斥工件且不承接聊天。前端需求条目独占全部白话收集和技术判断，正式创作条目只把合同编译为运行规则与HTML。普通模式的正则不在任何专项中生成。

### 5.2 构建单元

技术工件不能按“想到哪写到哪”切段。一个单元必须是当前语法中能够明确定位和局部检查的结构：

- Zod：一个顶层变量组或一个完整复合字段。
- YAML：一个完整顶层映射或一个完整文件。
- EJS：一个完整条件链及其中各个闭合阶段分支。
- HTML：数据读取、解析、渲染、交互、样式中的一个闭合职责区。
- 复合交付：一个完整文件就是一个单元。

每个单元开始前只做一条控制注释，然后立刻生成对应内容。控制注释按真实语法选择：

- JavaScript / TypeScript / CSS：`/* @qk-unit | ... */`
- YAML：`# @qk-unit | ...`
- HTML：`<!-- @qk-unit | ... -->`
- EJS：`<%# @qk-unit | ... %>`
- Vue 单文件组件：只在顶层块之间使用 `<!-- @qk-unit | ... -->`
- 严格 JSON：不在内部插入注释；把整个 JSON 视为一个不可拆单元。

不得把自然语言思考写进字符串、字段值、EJS 输出文本或用户最终能复制的内容。

### 5.3 围栏与多文件输出

单文件工件只开启一个代码围栏，直到文件完整闭合以后再关闭。复合交付按文件分别使用代码围栏，不能把 HTML、YAML 和 JavaScript 塞进同一个错误语言围栏。

在一个文件尚未闭合时，不得跳出围栏解释、道歉、复盘或询问。局部发现错误只重建当前局部；整体静态检查发现跨文件不一致时，必须重新输出受影响文件的完整修正版，不能只给用户一段无法定位的补丁。

### 5.4 完成条件

技术工件只有同时满足以下条件才允许写 `@qk-complete`：

- 所有约定文件都已输出。
- 没有未解决的 `...`、`TODO`、伪代码和让用户自行补齐的位置；当前官方固定模板本身要求保留的示意占位符必须原样保留，不得误删或擅自填成用户变量。
- 括号、引号、标签、EJS 块、代码围栏全部闭合。
- 文件名、变量路径、标签名、条目名、选择器和配置相互一致。
- 没有调用当前环境不存在的接口。
- 没有把讨论示例、控制注释以外的过程说明写进成品。
- 已完成静态校验，但没有把静态校验谎称为酒馆实测。

完成哨兵放在最后一个工件可接受的注释位置，清洗后不进入用户复制内容。哨兵之后不追加第二版、教程或“还可以继续优化”的扩写。

## 六、各工件的最低校验重点

### Zod 4

- `Schema` 命名、注册头尾与大小写一致。
- `z` 和 `_` 不重复导入。
- `z.prefault` 的值本身是合法输入。
- transform 不依赖第二个 context 参数，且重复 parse 不继续改变结果。
- 固定键、动态键、必需键和可清空对象选择正确。
- 只有用户明确要求的范围、容量与修复规则才进入 Schema。

### MVU 世界书

- initvar 的字段和类型完全对应 Schema。
- 更新规则中的路径、类型、范围与 Schema 一致。
- `_` 字段不进入 AI 更新规则。
- 变量列表与输出格式固定正文没有被改写。
- AI JSON Patch 路径不带 `stat_data`，EJS 与界面读取路径必须带 `stat_data`。

### EJS

- 一个工件只包含一个角色、一个蓝灯EJS条目和一份配置。
- 所有EJS标签、大括号、语义标签与条件链闭合。
- MVU变量读取带`stat_data`，默认值与initvar类型和值一致。
- `getwi`、`activewi`、写变量、聊天读取、装饰器、注入和正则等禁用能力均不存在。
- 条件边界无重叠、无遗漏，任一合法状态只输出一个阶段。
- 实际输出给模型的只包含角色专属标签和当前阶段差异正文，不包含条件、代码说明与控制注释。

### 前端

- 消息提取与源提示词的标签完全一致，并与用户提供的统一正则文件约定相符。
- 通过当前接口读取正确楼层，不使用 `DOMContentLoaded`。
- 不把未经转义的模型文本直接写入 `innerHTML`。
- iframe 宽度自适应，不使用 `vh` 强撑，不产生横向滚动，不让主体完全脱离文档流。
- 事件和应用在 `pagehide` 时按需要清理。
- 变量路径、DOM 选择器、缺省值和字段解析一一对应。

## 七、逐条知识核验与验收门禁

每个技术条目必须单独完成一次知识核验，不能因为相邻条目已经读过资料就凭记忆复用结论。未通过核验的条目不得开始写正文。

### 7.1 写前知识核验

开始某个条目前，必须：

1. 明确该条目的唯一工件、酒馆运行位置、输入依赖与不负责内容。
2. 重新读取与它直接相关的当前 `.cursor/rules`、`@types`、初始模板和可运行示例，只读当前工件需要的部分。
3. 再读取知识库与旧写卡器对应条目，只用于发现需求经验、历史写法和冲突，不能自动取得事实优先级。
4. 把接口名称、参数、事件签名、固定标签、固定模板、加载时机和配置要求逐项对照；资料冲突必须先记录并确定可信来源。
5. 无法从当前资料确认的能力不得凭感觉补写。若它是条目必要能力，先停止并继续查证；若不是必要能力，直接从本条目删除。

每个正式条目只能携带核验后仍然成立、且完成当前任务真正需要的知识。不能为了显得全面，把尚未核实或本任务用不到的 API、模板和示例一起塞入。

### 7.2 写后自查

条目正文写完后，必须依次完成：

1. **知识正确性检查**：正文中的语法、接口、参数、标签、固定结构和配置都能回指当前资料；没有沿用已被当前模板替代的旧写法。
2. **任务边界检查**：只生产一份 `active_workshop_task`；交谈、格式化与固定输出没有重新混合；未启用专项没有被召回。
3. **提示词污染检查**：参考例、旧变量、被否决方案、教程说明和检查过程不会进入最终工件；条目自身没有诱导模型提前套格式。
4. **正常路径模拟**：使用一组资料完整的新作者输入，确认条目能够走到正确终点。
5. **缺失依赖模拟**：缺少上游工件时只索取必要材料，不猜代码、不重建设计。
6. **冲突与坚持模拟**：用户提供无用变量、矛盾路径、旧格式或明确坚持保留低收益变量时，确认条目会给出真实判断并尊重最终决定。
7. **最终工件检查**：代码围栏、标签、括号、变量路径、文件名与配置闭合一致；无未授权新增、无省略、无伪造的运行结果。

固定输出条目还要把正文与当前初始模板逐项对照，不允许依靠记忆复写。涉及运行接口但本地资料自身冲突的条目，静态验收不能标记为“完全通过”；必须明确留下待实测项。

每份条目的核验来源、发现的冲突、修正内容、模拟输入和验收结论都要写入对应续接记录。只有结论为通过，才进入下一条；不能为了推进进度把“尚未验证”写成“已完成”。
