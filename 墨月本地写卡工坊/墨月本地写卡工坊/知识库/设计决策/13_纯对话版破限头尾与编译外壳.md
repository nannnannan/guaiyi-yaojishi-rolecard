# 纯对话版常驻头尾、COT与清洗

更新时间：2026-08-26

## 一、重构结论

旧方案错误地把简化 assistant 预填当成已验证的新尾部，并把自定义思维压缩成一行路由。现已全部删除。

当前方案使用七个固定开启核心条目：

1. 00_任务变量初始化。
2. 01_写卡工坊运行总纲-头部。
3. 02_事实资料与历史边界-常驻。
4. 03_专项隔离与工件完整性-常驻。
5. 90_专项思维链与连续创作-尾部。
6. 95_本轮用户输入锚点-尾部。
7. 99_直接进入预设思维-User尾部。

## 二、头部职责

运行总纲只处理所有专项共用的身份、破限与权限边界。事实资料条目只处理来源优先级和历史污染。专项隔离条目只处理状态、唯一任务和工件闭合。

三个常驻标签分开是为了让 COT 能准确召回，不把所有规则压成一个无法判断是否执行的长段落。它们不包含任何人设、世界观、MVU、EJS或前端教程。

## 三、尾部职责

90 尾部只展开一次 active_workshop_task，并把合同七字段变成自定义 COT 的实际执行程序。它不列举未启用专项，也不保存另一份任务状态。

95 尾部使用 lastUserMessage 把哥哥本轮发言重新放在长上下文末端。引用资料仍按 qk_source_integrity 作为资料处理，不能夺取操作指令身份。

99 尾部是 User 消息。它采用“定义 workshop-direct → 立即调用 → 最后再次禁止原生规划”的结构，不再伪造 assistant 已经开始回复。

## 四、思维与工件的关系

每轮先输出一段短而完整的任务寄存器，负责绑定本轮输入、合同、知识、事实、当前单元、边界、验收和停止位置。

dialogue 在寄存器后只完成一个对话单元。compile 在寄存器后按 qk-unit 与最终片段交替工作；因此思维没有在正文前一次性写完，也没有在正文开始后失去控制。

qk-unit 不是装饰。它必须实际引用常驻标签或专项知识规则，并写明当前局部使用的输入与完成条件。正则清洗后，用户只看到自然对话或完整工件。

## 五、无noass处理

本写卡预设不加入 noass、停止符和消息压缩。User 尾部中的 no-trans 只作为源结构边界，使用预设原生正则在发送前删除。

这项行为目前只有正则夹具通过。正式预设必须核对：该正则是否确实作用于尾部自定义 User 消息、标记是否完全消失、消息 role 是否仍为 User。未完成这三项前不能宣称尾部实机通过。

## 六、最小流式折叠

未闭合 thinking 在显示层被替换成一个默认折叠的 details，标题固定为“秋青子正在专心处理当前专项……”。

没有颜色主题、图标、动画、完成样式与思维内容美化。thinking 闭合后整段从最终显示中删除；下一轮历史也不会收到它。

## 七、当前验证

本地静态验证已经确认：

- 正则JSON可解析，共六条。
- 流式 thinking 会折叠，完整 thinking 会删除。
- 历史清洗保留 thinking 后的正文。
- XML、YAML、JavaScript和EJS的 qk 控制注释均被删除，真实工件保留。
- 普通对话不会被误删。
- 七个核心文件存在。
- 二十八个专项均只写入一个合同，合同 id 唯一。
- 每个专项声明的 knowledge 标签都存在。
- 90 尾部只读取一次 active_workshop_task，并召回三个常驻标签。

尚未验证：真实 SillyTavern Prompt Manager 顺序、User尾部标记清理、目标模型原生 reasoning、流式UI与长工件闭合。
