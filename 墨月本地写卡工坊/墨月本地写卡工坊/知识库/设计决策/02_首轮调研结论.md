# 首轮调研结论

更新时间：2026-08-25

## 一句话结论

新系统不应在三个环境里分别重写一套教程。更稳妥的起点是先形成一份共享的写卡知识、项目产物和校验规则，再分别接上传统问答、WTC agent、Web 界面和本地 Codex 工作流。

这仍是调研结论，不是已批准架构。

## 资料权威顺序

发生冲突时，暂按以下顺序判断：

1. 哥哥本次及后续明确要求。
2. `TODO_明月秋青写卡预设重构.md` 中已经确认的决策。
3. `AIRP人物生境写法教程.md` 的终稿结构与原则。
4. 旧三模式项目文档、旧预设及调色盘教程，仅作历史资料。

已发现一处术语不一致：AIRP 教程中段出现 `<角色名_性情>`，教程最终结构和新版 TODO 使用 `<角色名_人物性情>`。在正式规范统一前，暂以后者为准。

## AIRP 应保留的核心

- 基础信息：稳定、客观、足以识别角色的身份与身体/社会坐标。
- 生活结构：可持续发生作用的工作、技能、责任、关系、地点、资源与限制；不是日程表或物品清单。
- 人物性情：角色如何理解事件、在意什么、怎样理解自己及其内部张力；不预写固定反应公式。
- 场景表达：仅在前三层不足以自然产生多样表达时使用，可以省略。
- 已确认事实、作者解释和留白必须分开；未知不是缺陷，角色能继续生活就是重要的停止条件。

## 旧预设的结构性问题

1. 一个条目同时承担教程、提问、示例、生成、世界书写入、条目配置和自查，导致知识与流程无法独立维护。
2. 输出约束重复且互相叠加：既有通用 YAML 规则，也强制每轮输出 `<thinking>/<content>`；后者把内部推理格式当成产品协议，不宜继承。
3. 旧标签依赖人工维护递增 `idN`，同一角色的多个不同语义条目还共用标签。新版 TODO 提出的语义标签更容易检索和校验。
4. 旧角色基础完成后先写入世界书，再检查并询问是否同步修正；顺序应改为“生成 → 解析 → 预览 → 校验 → 用户确认 → 写入 → 回读”。
5. 世界书正文、触发策略和写入路径混在知识条目中。角色可见内容与酒馆配置必须分离。
6. 旧创作思路以调色盘、三面性和二次解释为主，已被 AIRP 方向取代，不能继续作为常驻核心。
7. 旧预设通过公共 CDN 加载 WTC 脚本；依赖来源、版本固定、失败提示和离线边界都需要在实现期重新决定。

## WTC 实现必须区分

首轮查看的本地 `src/wtc-aether` 与哥哥后来指定的上游 `mag/harness_update` 分支不是同一能力基线，后续不得混称为“当前 WTC”。

本地 `wtc-aether` 可借鉴：

- `/Characters`、`/Worldbooks`、`/Presets`、`/Schemas` 这类虚拟资源视图。
- 读、写、编辑、创建世界书、配置条目等工具的明确参数结构。
- 写入权限、备份和回滚思路。
- 有阶段的 agent 工作流，而不是无边界连续调用工具。

本地 `wtc-aether` 不可照搬：

- 当前管线面向互动小说创作，不是写卡项目；需要换成写卡阶段。
- 工具数量上限仍是旧草案数据，尚未由哥哥确认。

哥哥指定的 `mag/harness_update` 分支已确认：

- 注册 `Glob`、`Grep`、`Read`、`Write`、`Edit`、`Delete`、`CreateLorebook`、`TriggerSlash`、`GetAttribute`、`SetAttribute`。
- 世界书、角色和预设的读/写/删除权限按范围弹窗确认，并支持备份后持续授权；不能套用本地 `wtc-aether` 的自动授权结论。
- `AskUserQuestion` 有源码但在工具注册表中被注释，Agent 需要通过普通对话向用户提问。
- `TriggerSlash` 已经可用，但当前直接接受任意命令字符串；`/ejs` 验证可以建立在它上面，安全限制仍需另行设计。

## PNG 导出的已确认事实

现有 `tavern_sync.mjs` 已支持将角色 YAML 转为 `chara_card_v3` 数据，并把 `chara` 与 `ccv3` 元数据块写入头像 PNG。没有头像时只能得到 JSON 数据，不能凭空形成最终 PNG。

因此三个环境应共享角色卡字段与封装规则；Web 端可以实现等价的专用编码器，但不应直接把体积很大的现成打包文件当业务模块复制进去。头像生成、选择或裁切属于尚未讨论的产品问题。

## 本地 Codex 环境的初步边界

- 根 `AGENTS.md` 只放稳定规则、资料优先级、写入安全和总工作流。
- 具体知识按 Skill 拆分，例如 AIRP 人设、世界书、开场白、MVU、EJS、酒馆脚本、检查与导出。
- PNG 导出、结构校验等确定性操作交给脚本，不让模型靠自然语言重复拼装二进制格式。
- “青空莉”工程中的 Vue 偏好服务于酒馆内嵌页面；独立 Web 写卡器的框架必须等需求、部署与交互边界明确后再选。

## 新预设的首轮候选分层

以下仅供下一轮讨论：

1. 常驻内核：身份与沟通、事实优先与留白原则、资料优先级、阶段状态、写入安全、产物总契约。
2. 按需知识：AIRP 四层、世界观/世界书、开场白、NPC、MVU、EJS、脚本、检查与导出。
3. 纯对话控制器：完全不出现 WTC 指令，每次只解决当前缺口，能暂停、恢复、修改和确认；所需知识随预设装配。
4. WTC Agent 控制器：使用指定分支读取外部知识，负责读取上下文、提出问题、生成草稿、校验、预览和经确认后写入。
5. 平台适配：酒馆变量与世界书接口只留在酒馆层，不进入共享的人设知识。

## 尚未决定

- 三端共享产物是单一 YAML、目录式项目，还是两者并存。
- 新预设的精确条目清单、常驻条目数量和注入顺序。
- WTC 目标分支已指定；仍需决定发布时跟随分支还是固定到具体提交，以及是否增加 Slash 安全薄层。
- Web 端的框架、数据库、鉴权、多人/单人范围和 Zeabur 部署拓扑。
- 头像来源、PNG 预览、世界书可视化、开场白分支编辑的具体交互。
- MVU、EJS 与普通角色卡是一个项目类型的可选模块，还是独立产物类型。

## 下一步

下一轮只讨论并形成“新预设最小条目表”和每个条目的单一职责。确认后再逐条写规范；Web 和本地环境先保持兼容这一共享核心，不提前做界面或工程脚手架。
